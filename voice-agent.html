01 / How it works

From the caller's voice
to the kitchen screen.

A phone call travels through four systems in under two seconds. Here is every hop.

  1. 01

    The customer calls the restaurant

    The call routes over PSTN to Retell AI's platform, which answers instantly. No ringing, no waiting, no hold music.

  2. 02

    The agent listens and understands

    Retell's speech-to-text converts the caller's voice in real time. The LLM works out what they want — order, track, update or cancel — and runs the whole back and forth naturally.

    STT → LLM → TTS
  3. 03

    Retell fires an API tool call

    When the agent needs to place or change an order it sends an HTTP POST to the FastAPI backend with the extracted data: name, phone number, items, and any special requests.

    POST /createorder/ → FastAPI
  4. 04

    FastAPI writes to Firestore

    The async route handler validates the payload, checks for a duplicate order on that phone number, and writes the document with a server timestamp and pending status.

    FirestoreDB.create_order()
  5. 05

    The kitchen dashboard updates live

    Straight after the write, FastAPI broadcasts a WebSocket message through the ConnectionManager to every connected kitchen browser. A new row appears in real time with no refresh.

    manager.broadcast() → wss://
  6. 06

    The agent confirms to the customer

    FastAPI returns {"success": true}. The LLM reads it, speaks the confirmation, and wraps up the call.

    {"success": true} → TTS → customer

02 / Technology stack

Four technologies,
each doing what it does best.

Voice layer

Retell AI

Handles everything about the phone call: speech to text, the conversational LLM, text back to natural speech, and HTTP tool calls into the backend when action is needed.

Why: it abstracts all telephony. Zero speech processing code, only business logic.
API layer

FastAPI

Natively asynchronous, so it serves many requests without blocking. Retell calls the backend on every turn of a live call — a slow API becomes an awkward silence the customer hears.

Why: async throughput, native WebSocket, Pydantic validation built in.
Data layer

Firebase Firestore

Every order is a document in the orders collection with name, phone, items, special requests, status and timestamps. Phone number is the lookup key for every query.

Why: no migrations, no server management, scales on its own.
Real-time UI

Kitchen dashboard

An HTML page served by FastAPI through Jinja2. Current orders render server-side on load, then a native WebSocket keeps it live — new orders and status changes reflect instantly across every screen.

Why native WebSocket: no Redis, no broker. An in-memory ConnectionManager is enough.

03 / API surface

Nine endpoints.
Five run mid-call.

Five are invoked by Retell while the customer is still on the line. The rest power the kitchen dashboard and monitoring.

Method Endpoint Purpose Called by
POST /createorder/ Place a new order. Writes to Firestore and broadcasts to the kitchen. Retell · createorder
POST /trackorder/ Return the latest order status for a phone number. Retell · trackorder
POST /checkorder/ Return full order details for a phone number. Retell · checkorder
POST /updateorder/ Update or remove items on an existing order. Retell · updateorder
POST /cancelorder/ Cancel an order by setting its Firestore status to cancelled. Retell · cancelorder
POST /update-status/ Kitchen staff change an order's status by hand. Kitchen dashboard
GET / Serve the kitchen dashboard page. Kitchen browser
GET /health/ Health check returning {"status":"ok"}. HF monitor
WS /ws/kitchen/ Live socket pushing every order event to the kitchen. Kitchen browser

04 / Key features

What makes it
production ready.

  • Natural voice conversation The agent asks one question at a time, confirms before placing, and handles edge cases without falling apart.
  • Sub-second API response Async FastAPI answers fast enough that the customer never hears a pause. Slow APIs ruin a voice experience.
  • Real-time kitchen updates Native WebSocket broadcasting. Orders land on every kitchen screen the moment they are placed.
  • Payload envelope handling Retell wraps request data differently per call type. A custom extract_payload() helper unwraps arguments, data or payload envelopes every time.
  • Zero-server deployment Containerised with Docker on Hugging Face Spaces. Git push deploys, HTTPS is automatic, secrets live in encrypted environment variables.
  • Minimal project structure One main.py plus two modules. No app folders, no migrations, no boilerplate.
